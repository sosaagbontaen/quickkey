Internal Brief · Sam & Dom

QuickKey

A command layer that turns Premiere from a place you navigate into an instrument you play.

Status: Working prototype Premiere Pro (Mac) Proven on 26.3.2 · 27 Aug 2026
The Idea

One key, one intent — no menus, no modes

QuickKey is a Premiere Pro plugin that binds the things editors actually do to single keys. Press L and your default blur lands on the selected clip. Press B and the clip cuts at the playhead without leaving the selection tool. Every mapping is yours to define, including effects Premiere refuses to expose as commands.

We are not replacing Premiere. We are making it programmable.

The Problem

The cost isn't the work, it's the navigation

Our notes framed this as a screen real-estate problem, but that's the symptom. The real issue is action cost: Premiere makes you travel to a location to perform an action, so every intent becomes a sequence of trips. The only reason six panels must stay on screen is that every action lives inside one of them.

Premiere today
select clip → find Effects panel → search "blur" → pick variant → drag onto clip → open Effect Controls → set amount
7 actions
With QuickKey
select clip → press L
2 actions

Second half of the pain: modal tools. C puts you in blade mode until V takes you out — the app asks you to hold state it should hold itself. Final Cut's B cuts and returns. Every mode you have to remember is a tax paid thousands of times a day.

Why a Product

Adobe's own remapping has a hard ceiling

Premiere lets you rebind roughly a thousand commands — but only commands that already exist in a menu. "Apply my default blur" is not a menu item, so it can never be a key. That gap — between what Premiere lets you bind and what editors actually do — is the entire product surface.

What we have to beat

  • Stream Deck, Loupedeck, Tourbox, Keyboard Maestro. Editors already use these to collapse UI steps. Our claim: they replay clicks at fixed coordinates and are blind to project state — they can't know which clip is selected or what your default blur is, so they break the moment your layout shifts. QuickKey lives inside Premiere and reads that state. Now demonstrated: the same keystroke hit two different clips purely because the selection changed.
  • Existing panels (Excalibur and similar). Worth an hour of study — what they do, what they charge, and what they conspicuously don't touch.
  • Final Cut Pro itself, which mostly doesn't have this problem — but Adobe is the professional and academic standard, and switching costs are enormous. That's why the plugin market exists at all.
Prototype

Answered: yes. It works.

Can a plugin apply an effect to the currently selected clip?

Proven · Premiere 26.3.2

A running prototype applies a real Gaussian Blur to whatever clip is selected, triggered by a keystroke, while the editor's hands stay in the timeline. Two presses on two different clips, straight from the log:

19:16:28 Default Blur -> qkApplyEffect("Gaussian Blur") -> OK: applied Gaussian Blur to 1 clip(s): Sample Media Clip 1.mp4 19:16:30 Default Blur -> qkApplyEffect("Gaussian Blur") -> OK: applied Gaussian Blur to 1 clip(s): Sample Media Clip 17.mp4

It followed the selection. That is the whole difference between QuickKey and a macro.

Why it takes four pieces

Premiere blocks this two separate ways, and each block needs its own answer.

1Hotkey daemonA background agent app catches the key at the OS level. Premiere cannot bind a key to a plugin, so the trigger has to live outside it. Uses the Carbon hotkey API — no Accessibility permission prompt, which matters enormously for install conversion.
2BridgeHands the command to the panel. Also our dev harness — it lets us query a running Premiere from a terminal in under a second.
3Public APIReads which clip is selected. This API cannot apply effects.
4QE layerAdobe's undocumented internal layer actually applies the effect. It has no concept of selection. Confirmed alive in 26.3.2.

The product is the seam between 3 and 4. Neither layer can do the job alone; Premiere ships no bridge between them. That is the gap QuickKey occupies — and it explains why nobody has built this: not difficulty, but that the capability is undocumented and unsupported.

What is still fake

  • Modifier combos, not bare keys — and this one is settled, not guessed. We bound bare B E S M and they went dead in every application on the machine, mid-sentence, in another app. The OS consumes a registered hotkey before any of our code runs, so the "only while Premiere is frontmost" check can decide whether to act but can never hand the key back. A bare binding is global by construction.

    Consequence: true single-key binding requires an event tap and an Accessibility grant — a scarier install and a permission prompt we had been pleased to avoid. Modifier combos work today with no permission at all. The panel now refuses to save a bare binding.
  • Modes are a cheat. CtrlOpt2 calls Premiere's own setWorkspace. It demos well but inherits exactly the workspace clunkiness from the original notes.
  • No text-field awareness. Even with an event tap, a binding must go quiet while the editor is typing in a rename box or a search field. Detecting that from outside Premiere is unsolved.
  • No parameters, no installer. Effects land at their defaults. There is no mapping editor — bindings are a JSON file.
Open Risks
Is it "one key" or "one keystroke"?
A bound bare key is swallowed everywhere, permanently — proven the hard way. So either we ship modifier combos permission-free, or we take an Accessibility grant to get real single keys. Note the pitch survives either way: CtrlOptB is still one gesture replacing seven. Worth asking Dom which he'd actually rather install.
Is CEP a dead end?
The prototype runs on CEP, which Adobe is replacing with UXP. Frame.io ships a UXP plugin here that already calls getActiveSequence and getSelection, so selection survives the migration — unknown whether UXP can apply effects, or whether the QE layer is reachable from it. Worth answering before we build UI on CEP.
What if Adobe closes the QE layer?
It is undocumented and unsupported; a point release could remove it. That is the moat and the mortality in one sentence. Adobe also has a long history of acquiring plugins that fix its own gaps (FilmImpact) — both the risk and the exit.
Do editors pay, or just complain?
Unvalidated. We have two data points — us. Needs 5–10 conversations with working editors before we scope a v1.
Is the command set personal or universal?
If Sam's and Dom's top-10 lists barely overlap, we ship a mapping editor. If they mostly match, we ship opinionated defaults — a much easier product to sell.
